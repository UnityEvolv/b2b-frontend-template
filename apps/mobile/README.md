# Mobile

React Native with Expo, in the same workspace as the web apps, consuming the
same packages: `@b2b-template/api` (the typed client), `@b2b-template/client`,
`@b2b-template/core`, `@b2b-template/i18n` and `@b2b-template/theme`.

Sign-in (with a second factor), invitations and account links from emails,
the notification feed, the profile and sessions, and switching or leaving an
organization. [docs/mobile-and-desktop.md](../../docs/mobile-and-desktop.md)
compares it with the desktop shell and lists the known gaps.

## Run

```sh
npm run start -w @b2b-template/app-mobile       # Metro; press a for an emulator, or scan with Expo Go
npm run android -w @b2b-template/app-mobile     # build and run on the emulator or the plugged-in device
```

It reads the build's configuration:

| variable | meaning |
| --- | --- |
| `EXPO_PUBLIC_APP_NAME` | the name under the icon (default `B2B App`) |
| `EXPO_PUBLIC_APP_SCHEME` | the app's link scheme (default `b2bapp`) |
| `EXPO_PUBLIC_APP_BUNDLE_ID` | the Android package and iOS bundle identifier (default `com.example.b2bapp`) |
| `EXPO_PUBLIC_API_ORIGIN` | where the API gateway is, e.g. the backend on your LAN address for a real device |
| `EXPO_PUBLIC_API_ORIGIN_<SERVICE>` | one service's own origin, as a laptop's compose stack gives each a port (`..._IDENTITY`, `..._USER`, …) |
| `EXPO_PUBLIC_APP_LINK_HOST` | the web app's host, which the emails link to; Android opens those links in the app |
| `EXPO_PUBLIC_EAS_PROJECT_ID` | set by `eas init`; turns on update delivery |

Put them in `apps/mobile/.env` (ignored) or the shell. `EXPO_PUBLIC_*`
values are inlined at build time; a change needs a rebuild or an update.

## Sign-in and the session

The same client as web (`@b2b-template/client`), email first. A local account
types a password; an organization with its own identity provider opens the
**system browser** (`expo-web-browser`, never a webview) with `client=mobile`
and a PKCE challenge, the same hand-off as the desktop app; the identity
service returns to `<scheme>://auth/callback` with a one-time code the app
trades, with the PKCE verifier, at `POST /identity/v1/sign-in/exchange`. The
identity service's session cookie is kept in the platform keystore
(`expo-secure-store`) and presented by hand; access tokens live in memory
only.

## Links from emails

An invite, a confirmation link, a password link and a required authenticator
set-up open in the app: `<scheme>://accept-invite?token=…` always, and the
email's own `https://<EXPO_PUBLIC_APP_LINK_HOST>/accept-invite?token=…` once
Android has verified the host. Verification needs the host to serve
`/.well-known/assetlinks.json` naming the bundle identifier and the signing
certificate's SHA-256 fingerprint. The paths are in `src/link-paths.json`,
read by both the config and the app.

## A real Android device

```sh
npm run install:device -w @b2b-template/app-mobile   # release APK, signed with the debug keystore, adb install
```

Needs the Android SDK and a JDK, and the device in developer mode with USB
debugging on. The native project (`android/`) is generated by
`expo prebuild` and not committed.

## Updates without reinstalling

`expo-updates` is configured; it needs an Expo project:

```sh
npx eas-cli login
npx eas-cli init                               # creates the project; note the id
EXPO_PUBLIC_EAS_PROJECT_ID=<id> npm run install:device -w @b2b-template/app-mobile
npx eas-cli update --channel preview --message "..."   # every installed device picks it up on next launch
```

Builds and updates meet on a channel (`eas.json`: `development`, `preview`,
`production`) and a runtime version (the app version). A change to native
code or to `app.config.ts` is a new build; a change to JavaScript is an update.
